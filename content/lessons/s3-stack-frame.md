## 讲解

### 一次函数调用，在栈上留下一块"帧"
程序运行时，栈是一段从高地址向低地址增长的内存。每调用一个函数，就在栈顶"切"出一块空间给这次调用用，这块空间叫**栈帧**（stack frame，也叫活动记录）。函数返回时，整块帧被丢弃，栈指针回到调用前的位置。

一个栈帧里通常有四样东西：

1. **参数**（超出寄存器数量的部分，或者 32 位下全部参数）；
2. **返回地址**：`call` 指令自动压进来的，函数结束时靠它回到调用点；
3. **保存的旧 `ebp`**：函数序言 `push ebp` 压进来的，用来串起调用链、也用来在返回时恢复上一层的帧指针；
4. **局部变量**：函数体里声明的自动变量，包括数组和结构体。

所以"局部变量在栈上"并不是一句抽象的话：它就是被摆在当前帧里，和返回地址做邻居。

### 函数序言与函数尾声：帧是这么建立和拆除的
编译器在每个函数开头插入**序言**（prologue），在结尾插入**尾声**（epilogue）。32 位 x86 上最经典的写法是：

```c
push ebp            /* 保存调用者的帧指针 */
mov  ebp, esp       /* 让 ebp 指向本帧的"基准位置" */
sub  esp, N         /* 给局部变量腾出 N 字节 */
...                 /* 函数体 */
mov  esp, ebp       /* 丢弃局部变量（esp 直接抬回来） */
pop  ebp            /* 恢复调用者的帧指针 */
ret                 /* 弹出返回地址，跳回去 */
```

`ebp` 一旦固定下来，帧里每个东西的位置就都是**编译期常量偏移**：参数在 `ebp+8` 往上，返回地址在 `ebp+4`，旧的 `ebp` 在 `ebp+0`，局部变量在 `ebp-4` 往下。

这就是"栈帧布局"的全部含义。看一张完整的图（地址只是示意，真实地址每次运行都不同，而且开了 AddressSanitizer 后布局还会变）：

```memory title="32 位 cdecl 的一个栈帧（地址为示意，真实值不可依赖）"
地址 | 内容 | 是谁放的 | 相对 ebp
0x7ffd1000 | 参数 c | 调用者 | ebp+16
0x7ffd0ffc | 参数 b | 调用者 | ebp+12
0x7ffd0ff8 | 参数 a | 调用者 | ebp+8
0x7ffd0ff4 | 返回地址 | call 指令 | ebp+4
0x7ffd0ff0 | 调用者的 ebp | 函数序言的 push ebp | ebp+0
0x7ffd0fec | 局部变量 x | 被调用者 | ebp-4
0x7ffd0fe8 | 局部变量 y | 被调用者 | ebp-8
```

几个容易忽略的细节：

- **`ebp+0` 存的是旧的 `ebp`，不是返回地址**。返回地址在 `ebp+4`——这是初学者最常见的错位一格；
- 局部变量的偏移是**负数**，而且是从 `ebp-4` 开始向低地址走；`char` 可能占 1 字节，但编译器经常会把它塞进 4 字节的槽里，还可能为了对齐留出空洞；
- 帧里除了这些"看得见"的东西，还可能有编译器插入的填充、金丝雀（`-fstack-protector`）、以及 AddressSanitizer 的红区。

### 为什么能找回返回地址
返回地址不是谁特意存起来的，而是 `call` 指令的副产物：`call` 做两件事——把**下一条指令的地址**压栈，然后跳到函数入口。于是函数一进来，`[esp]` 就是返回地址。

函数序言又压了一个 `ebp`，所以返回地址的位置从 `esp` 变成了 `esp+4`；等 `ebp` 建立起来之后，它就固定在 `ebp+4`。尾声里 `pop ebp` 把栈指针抬回返回地址处，`ret` 正好弹出它。

这就解释了三件事：

- 为什么函数"返回后能继续执行调用点的下一句"——返回地址一直在栈上；
- 为什么**栈溢出会破坏返回地址**——写越界的局部数组时，超出部分正好覆盖返回地址，`ret` 就跳到垃圾地址（经典的栈缓冲区溢出攻击）；
- 为什么 `__builtin_return_address(0)` 能拿到它——编译器知道它在 `ebp+4`（或帧指针链里），直接读出来即可。

也正因为返回地址是"回到哪条指令"，**同一个调用点被反复执行时，返回地址是同一个值**。下面的程序只比较相等性，从不打印地址的数值：

```c run id=sf-retaddr
#include <stdio.h>

static void *g_slot[3];                  /* 只存返回地址，不打印它的数值 */

static void capture(void **where) {
    *where = __builtin_return_address(0);
}

int main(void) {
    for (int i = 0; i < 2; i++) {
        capture(&g_slot[i]);             /* 同一个调用点，执行两次 */
    }
    capture(&g_slot[2]);                 /* 另一个调用点 */
    printf("同一调用点两次：返回地址%s\n", g_slot[0] == g_slot[1] ? "相同" : "不同");
    printf("不同调用点：返回地址%s\n", g_slot[0] == g_slot[2] ? "相同" : "不同");
    return 0;
}
```
```output
同一调用点两次：返回地址相同
不同调用点：返回地址不同
```

注意：地址的**数值**绝对不能拿来当程序逻辑。原因有两个：操作系统每次运行都会随机化加载地址（ASLR），所以两次运行同一个程序，数值就不一样；而且优化级别、插桩、编译器版本都会改变它。能依赖的只有"是不是同一个位置"这种相对关系。

### 每次调用都是全新的帧
局部变量之所以"不跨调用保留"，不是因为编译器在返回时把它清零了，而是因为**下一次调用的帧可能根本不在同一个位置**，即使在同一位置，那块内存也会被后续调用覆盖。所以每次进入函数，局部变量都是"刚出生"的状态，里面是不确定的值：

```c run id=sf-fresh
#include <stdio.h>

static int tick(void) {
    int n = 0;          /* 每次调用都重新创建，初值 0 */
    n++;
    return n;
}

int main(void) {
    printf("%d %d %d\n", tick(), tick(), tick());
    return 0;
}
```
```output
1 1 1
```

三次都返回 1，而不是 1、2、3——因为每次调用都拿到一块新的（或至少是被重置的）帧。想让值跨调用保留，必须用 `static` 局部变量（存储期变成整个程序）或者全局变量，那是另一条路。

### 递归：同一个函数的多份帧同时存在
递归不是什么"函数调用自己"的魔法，它就是普通的函数调用，只不过被调用的函数和调用者是同一段代码。每次递归都会**新建一个帧**，里面各有一份自己的参数和局部变量。所以 `down(2)` 执行到最深处时，栈上同时有三份 `down` 的帧：

```memory title="down(2) 执行到最深处的栈（地址为示意；每层都比上一层更靠近低地址）"
地址 | 内容 | 属于哪一层 | 说明
0x7ffd0ff4 | 返回地址 | main 调用 down(2) | 回到 main 里 call 之后的那条指令
0x7ffd0ff0 | n = 2 | down(2) 的帧 | 这一层的参数，独立一份
0x7ffd0fec | 返回地址 | down(2) 调用 down(1) | 递归调用点的下一条指令
0x7ffd0fe8 | n = 1 | down(1) 的帧 | 与上一层的 n 互不影响
0x7ffd0fe4 | 返回地址 | down(1) 调用 down(0) | 
0x7ffd0fe0 | n = 0 | down(0) 的帧 | 最深的一层，不再递归
```

帧是"后进先出"的：最后创建的 `down(0)` 最先返回，它的帧先被丢弃，然后才是 `down(1)`、`down(2)`。这直接决定了递归的两阶段——**递推**（一路建帧下去）和**回归**（一路拆帧回来）：

```c run id=sf-recursion
#include <stdio.h>

static void down(int n) {
    printf("进入 n=%d\n", n);
    if (n > 0) {
        down(n - 1);
    }
    printf("离开 n=%d\n", n);
}

int main(void) {
    down(2);
    return 0;
}
```
```output
进入 n=2
进入 n=1
进入 n=0
离开 n=0
离开 n=1
离开 n=2
```

"进入"按 2、1、0 的顺序打印，"离开"按 0、1、2 反过来——这不是巧合，而是帧的创建/销毁顺序。**任何"进入时打印、离开时再打印"的递归，输出都必然是两个方向**，理解这一点是看懂所有递归输出的基础。

### 函数返回后，帧就作废了
函数返回的一瞬间，`esp` 被抬回调用前的位置，那块帧在逻辑上已经不存在了。里面的字节可能还在（没人特意清零），但它已经不属于你：下一次调用会重新占用它。所以返回"指向局部变量的指针"是最经典的悬垂指针：

```c run id=sf-dangling expect=RE warnings=allow
#include <stdio.h>

static int *make_local(void) {
    int value = 42;
    return &value;                  /* 错：返回的是本层栈帧里的变量 */
}

int main(void) {
    int *p = make_local();
    printf("%d\n", *p);             /* 帧已经回收，这块内存不再属于我们 */
    return 0;
}
```

编译器其实已经看出问题了，会报 `address of stack memory associated with local variable 'value' returned` 这样的警告；而本平台的 AddressSanitizer 更进一步，在真正读取时直接把它抓成 `stack-use-after-return`，判 `RE`。没有检测工具时，这类程序可能"碰巧"打印出 42，然后在某次改动后突然崩溃——这正是它危险的地方。

### 栈为什么会溢出
栈的大小在程序启动时就定了（Windows 默认 1MB，Linux 默认 8MB 左右；本平台的判题器为了跑大数组把它调大了，但它仍然有限）。每层调用都要占一块帧，递归深度一大，帧就一层层叠上去：

```
总栈用量 = 每层帧大小 × 递归深度
```

当它超过栈的上限，程序就会写到栈保护区之外，被操作系统或 AddressSanitizer 拦下——**栈溢出**。它不是"返回一个错误"，而是程序立刻死掉，本平台判 `RE`：

```c run id=sf-overflow expect=RE
#include <stdio.h>

static long long sum_to(long long n) {
    long long pad[4];               /* 每层都要占一块栈空间 */
    pad[0] = n;
    pad[1] = n + 1;
    pad[2] = n + 2;
    pad[3] = n + 3;
    if (n == 0) {
        return pad[0];
    }
    return pad[0] + sum_to(n - 1);
}

int main(void) {
    printf("%lld\n", sum_to(2000000));
    return 0;
}
```

把 `2000000` 改小（比如 1000）程序就正常了，说明问题不在算法，而在"帧太多"。这也解释了为什么递归算法必须关心**深度**：分治递归的深度是 log n，通常没事；线性递归的深度是 n，n 到几十万就会撞上栈上限。实在需要很深的递归时，要么改成迭代（用堆上的显式栈），要么调大栈（编译器/系统选项，不可移植）。

### 被调用者保存的寄存器
函数序言里除了 `push ebp`，有时还会看到 `push rbx`、`push r12` 之类。这是另一条约定：某些寄存器（`rbx`、`rbp`、`r12`–`r15`）由**被调用者**负责保存和恢复，另外一些（`rax`、`rcx`、`rdx`、`rsi`、`rdi`、`r8`–`r11`）由**调用者**自己负责。原因很实际：调用者可能正在用 `rbx` 存一个值，它不希望一次函数调用就把这个值弄丢。

这也解释了为什么帧的大小往往比"局部变量之和"更大：里面还塞着被保存的寄存器、对齐填充和对齐到 16 字节的栈指针。**帧的大小是编译器的实现细节**，不同优化级别、不同编译器都可能不同——所以永远不要假设"`int` 局部变量一定在 `ebp-4`"，只能把它当作理解原理的模型。

## 编译与运行

用 gcc 或 clang 编译：

```bash
gcc -std=c17 -Wall -Wextra frame.c -o frame
./frame
```

```bash
clang -std=c17 -Wall -Wextra frame.c -o frame
./frame
```

想看真实的帧布局，用 `-S` 生成汇编（本平台实测，删掉了 SEH 相关指令）：

```bash
clang -std=c17 -O0 -S frame.c -o frame.s
```

对一个 `int add(int a, int b) { int sum = a + b; return sum; }`，生成的代码大致是：

```asm
add:
	subq	$16, %rsp          # 序言：给本帧留 16 字节
	movl	%ecx, 12(%rsp)     # 参数 a 存进帧里
	movl	%edx, 8(%rsp)      # 参数 b 存进帧里
	movl	12(%rsp), %eax
	addl	8(%rsp), %eax
	movl	%eax, 4(%rsp)      # 局部变量 sum
	movl	4(%rsp), %eax      # 返回值放进 eax
	addq	$16, %rsp          # 尾声：抬回栈指针
	retq
```

对照着看 `main` 的序言/尾声，`push rbp`、`sub rsp`、`lea rbp, [rsp+N]`、`add rsp`、`pop rbp`、`ret` 一一对应：

```asm
main:
	pushq	%rbp
	subq	$48, %rsp
	leaq	48(%rsp), %rbp     # rbp 指向本帧基准
	...
	addq	$48, %rsp
	popq	%rbp
	retq
```

几个有用的开关：

- `-fno-omit-frame-pointer`：强制保留帧指针。`-O2` 默认会省掉 `ebp`，改用 `rsp` 相对寻址，于是"帧指针链"就断了；
- `-fstack-protector-all`：在帧里插入金丝雀，函数返回前检查它有没有被越界写覆盖，能抓住一部分栈溢出；
- `-fsanitize=address`：本平台默认开启。它会在每个局部变量周围插入红区（redzone），**帧布局会因此明显改变**——这也是为什么本页的所有地址都只画示意图。

## 常见错误

### 返回局部变量的地址 [RE]
函数返回后帧就被回收了，指针指向的是"别人的地盘"。写的时候可能没感觉，读的时候才炸；本平台会把它判成 `RE`（AddressSanitizer 报 `stack-use-after-return`）。正确做法是由调用者提供缓冲区，或者用 `malloc`（第 5 阶段）。

```c run id=sf-err-local-array expect=RE warnings=allow
#include <stdio.h>

static char *name_of(int id) {
    char buf[16];                    /* 局部数组：随帧一起消失 */
    snprintf(buf, sizeof buf, "user%d", id);
    return buf;                      /* 错：返回的是局部数组的地址 */
}

int main(void) {
    char *p = name_of(7);
    printf("首字符 = %c\n", p[0]);   /* 读一个字节：ASan 能抓到 */
    return 0;
}
```

### 以为递归会共用同一个局部变量 [WA]
每一次调用（包括递归的每一层）都有自己独立的帧，局部变量也是各自一份。子调用里怎么折腾，都不会改到父层的变量：

```c run id=sf-per-frame
#include <stdio.h>

static void show(int n) {
    int copy = n;                    /* 本帧自己的局部变量 */
    if (n > 0) {
        show(n - 1);                 /* 子调用有自己的 copy，改不到这里 */
        printf("回来后：n=%d，copy=%d\n", n, copy);
    }
}

int main(void) {
    show(2);
    return 0;
}
```
```output
回来后：n=1，copy=1
回来后：n=2，copy=2
```

子调用返回后，`n` 和 `copy` 都还是原来那个值——这就是"每层一帧"的直接证据。反过来说，如果真想让所有层共享一个计数器，就必须用 `static` 局部变量或全局变量；那时改的才是同一个对象。

### 递归太深，栈溢出 [RE]
每层递归都要占一块帧，线性递归 100 万层就是几千万到上亿字节。本平台判 `RE`（`AddressSanitizer: stack-overflow`），普通环境则直接段错误。判断方法：估算"每层帧大小 × 最大深度"，超过几 MB 就要警惕；能改迭代就改迭代。

### 以为 `-O2` 下还能靠打印地址推算帧布局 [WA]
`-O2` 会把局部变量放进寄存器、把帧指针省掉、把相邻的帧合并，甚至把整个函数内联掉——这时"地址"根本不存在，`&x` 只会强制编译器在栈上临时造一个副本。用优化后的地址去验证布局，得到的结论一定是错的。要看布局就固定用 `-O0 -fno-omit-frame-pointer`，并且只把它当模型看。

### 把大数组放在栈上 [RE]
栈的容量是有限的（系统默认几 MB，本平台调大了，但仍然有限）。`int a[10000000]` 是 40MB，很可能直接崩溃；即使侥幸没崩，也会让递归的可用深度大幅减少。几百 KB 以上的数组应该用 `static`（存储期变长但不占栈）或 `malloc`（第 5 阶段）。

## 客观题

### q-s3-stack-frame-1 single
32 位 x86 的 cdecl 调用约定下，函数 `f` 已经执行完序言 `push ebp; mov ebp, esp; sub esp, 16`。此时 `[ebp+4]` 和 `[ebp+8]` 里分别是什么？

- [x] `[ebp+4]` 是返回地址，`[ebp+8]` 是 `f` 的第 1 个参数
  > 正确。`call` 先把返回地址压栈，序言再压入旧的 `ebp`，所以返回地址落在 `ebp+4`；参数从右往左压，第 1 个参数最后压入、紧贴返回地址上方，正好是 `ebp+8`。`[ebp+0]` 才是旧的 `ebp`。
- [ ] `[ebp+4]` 是旧的 `ebp`，`[ebp+8]` 是第 1 个参数
  > 错。旧的 `ebp` 是序言里 `push ebp` 压进去的，位置在 `ebp+0`；把 `ebp+0` 和 `ebp+4` 记反，会导致推算参数偏移时整体错 4 字节。
- [ ] `[ebp+4]` 是返回地址，`[ebp+8]` 是 `f` 的第 2 个参数
  > 错。参数虽然从右往左压，但读的时候按地址从小到大就是声明顺序：`ebp+8` 是第 1 个参数，第 2 个在 `ebp+12`。第 2 个参数在 `ebp+8` 的说法，等于把"压栈顺序"和"内存顺序"混为一谈了。
- [ ] 两者都在 `ebp` 以下，因为它们都是本次调用产生的
  > 错。返回地址和参数都在 `ebp` **之上**（更高的地址），只有局部变量在 `ebp` 之下。`ebp` 的意义正是"把本帧的参数区和局部变量区分开"：往上是被调用者无权改的调用者数据，往下才是本帧自己的空间。
