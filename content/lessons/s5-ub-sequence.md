## 讲解

### 一条语句里，先算哪一半

C 的表达式由两种东西组成：**值计算**（value computation，算出这个子表达式的值）和**副作用**（side effect，改一个对象、写一个文件、调用一个函数）。`i++` 同时做两件事：值计算得到 `i` 的旧值，副作用把 `i` 加 1。

标准对"谁先谁后"有一套明确的规则，核心只有一句（C17 6.5p2）：

> 如果对一个标量对象的副作用，相对于**同一个对象**的另一个副作用或值计算是**未排序**的，行为未定义。

"排序"（sequenced before）是从 C11 开始用的正式术语，取代了老书上说的"序列点"。判 UB 只需要查三件事：

1. 这些访问是不是在**同一个完整表达式**里（两条语句之间永远有 `;` 隔着，安全）；
2. 它们是不是**同一个对象**（`i` 和 `j` 互不相干）；
3. 它们之间有没有**排序关系**，且至少有一个是写。

三条同时成立才是 UB。所以把语句拆开写，永远不会出事：

```c run id=seq-two
#include <stdio.h>

int main(void) {
    int i = 0;
    i++;                          /* 第一条语句：读完就改，改完结束 */
    i++;                          /* 第二条语句：`;` 保证上一条已经彻底完成 */
    printf("i = %d\n", i);

    int j = i++;                  /* 值计算拿走 2，副作用把 i 变成 3 */
    printf("j = %d, i = %d\n", j, i);
    return 0;
}
```
```output
i = 2
j = 2, i = 3
```

标准里明确提供"排序关系"的位置只有这么几个，记住它们就等于记住了哪里安全：

| 位置 | 保证的先后关系 |
|---|---|
| `;` 与完整表达式结束 | 前一条语句的全部副作用都已完成 |
| 逗号运算符 `,` | 左操作数先于右操作数 |
| `&&`、`||` | 左操作数先于右操作数（短路时右边根本不求值） |
| `?:` | 条件先于被选中的那个分支；没被选中的分支不求值 |
| 函数调用 | 所有实参的值计算先于函数体；**实参之间没有顺序** |
| 库函数返回 | 调用期间的副作用对调用之后是可见的 |

注意表里**没有**算术运算符。`a + b` 的两个操作数之间没有任何顺序保证，这正是几乎所有"求值顺序 UB"的来源。逗号、`&&`、`?:` 之所以安全，是因为它们是标准点名的排序点：

```c run id=seq-points
#include <stdio.h>

int main(void) {
    int i = 0;
    int a = (i++, i++, i);         /* 逗号运算符：左先右后，三次访问全部有序 */
    printf("a = %d, i = %d\n", a, i);

    int k = 0;
    if (k++ == 0 && k++ == 1) {    /* && 是排序点：左边算完才轮到右边 */
        printf("&& 左边算完才轮到右边：k = %d\n", k);
    }

    int x = 7;
    int y = (x > 0) ? x++ : x--;   /* 只求值一个分支，另一个分支的副作用不存在 */
    printf("y = %d, x = %d\n", y, x);
    return 0;
}
```
```output
a = 2, i = 2
&& 左边算完才轮到右边：k = 2
y = 7, x = 8
```

### `i = i++` 到底发生了什么

把 `i = i++;` 拆成机器真正做的四步（初始 `i == 5`）：

1. 算出赋值号左边 `i` 的地址，记下来；
2. 求值 `i++`：读 `i` 得到 5（这就是 `i++` 的值）；
3. `i++` 的副作用：把 6 写进 `i`；
4. 赋值的副作用：把第 2 步拿到的 5 写进 `i`。

问题出在第 3 步和第 4 步：**它们都是对同一个 `i` 的写，而标准没有规定谁先谁后**。于是"写 6 再写 5"得到 5，"写 5 再写 6"得到 6，标准对两种都不反对——它根本不要求程序有结果。这就是未定义行为，不是"结果不确定但至少是 5 或 6 之一"：编译器可以直接把这段代码删掉、可以让它崩溃、也可以在周围插入任何东西。

本平台（Clang，x86-64 Windows）实测：`-O0` 与 `-O2` 都给 5。下面两段代码一模一样，只有一个编译选项不同：

```c run id=seq-self-O0 warnings=allow nocheck reason="i = i++ 是未定义行为，标准允许任意结果"
#include <stdio.h>

int main(void) {
    int i = 5;
    i = i++;                      /* 两个未排序的写：UB */
    printf("i = %d\n", i);
    return 0;
}
```

```c run id=seq-self-O2 opt=-O2 warnings=allow nocheck reason="i = i++ 是未定义行为，标准允许任意结果"
#include <stdio.h>

int main(void) {
    int i = 5;
    i = i++;                      /* 同一个 UB，只是换了优化级别 */
    printf("i = %d\n", i);
    return 0;
}
```

**两档结果一致，恰恰是这件事最危险的地方**：你做了"对照实验"、看到两次都是 5，很容易得出"这段代码语义确定"的结论。实际上这只能说明"这一版编译器的这一条代码路径碰巧这么选了"。换一个编译器、换一个版本、甚至在前面多写一行 `printf`，都完全可能变成 6 或者别的东西。判断标准只有一条——**标准有没有规定**，而不是"我这儿跑出来是多少"。

顺便说一句：Clang 其实**已经在编译时警告你了**：

```text
warning: multiple unsequenced modifications to 'i' [-Wunsequenced]
```

`-Wunsequenced` 包含在 `-Wall` 里。这类 UB 是目前 sanitizer 抓不到的（UBSan 没有"未排序修改"这项检查），所以**编译警告比运行期检查更管用**——看到这条警告就当编译错误处理。

### 各种变体：UB、未指定、完全合法

把常见的写法排一张表，注意"未指定（unspecified）"和"未定义（undefined）"是两件完全不同的事：前者是"标准给了几个合法答案，编译器挑一个"，后者是"标准什么都没说"。

| 写法 | 结论 | 原因 |
|---|---|---|
| `i = i++` | **UB** | 两个未排序的写 |
| `i = i++ + 1` | **UB** | 同上，加法不提供顺序 |
| `a[i] = i++` | **UB** | 读 `i` 当下标与写 `i` 未排序 |
| `f(i++, i++)` | **UB** | 实参之间没有顺序，两次写 |
| `printf("%d %d", i++, i++)` | **UB** | 同上 |
| `f(i++, i)` | **UB** | 实参之间没有顺序，一写一读 |
| `(i++, i++)` | 合法 | 逗号运算符是排序点 |
| `i++; i++;` | 合法 | `;` 是排序点 |
| `f(g(), h())`（两个函数互不影响） | 合法但**未指定**顺序 | 谁先算都行，结果一样 |
| `a[i] = i; i++;` | 合法 | 拆成两句，顺序被 `;` 固定 |

倒数第三行和倒数第四行值得单独体会。`f(g(), h())` 里先算 `g` 还是先算 `h`，标准**没有规定**，但两个顺序都是合法的，程序仍然有确定的结果——这叫未指定行为。只有当两个实参互相干扰（比如都改同一个全局变量）时，才升级成 UB。

下面这段代码就是"未指定但合法"：`note(1)` 和 `note(2)` 谁先被调用不确定，但两者都只往计数器里累加，所以 `calls` 和 `total` 一定是 2 和 3：

```c run id=seq-args
#include <stdio.h>

static int calls;
static int total;

static int note(int v) {
    calls++;
    total += v;
    return v;
}

static int add2(int a, int b) {
    return a + b;
}

int main(void) {
    int s = add2(note(1), note(2));   /* 两个实参的求值顺序：标准未指定 */
    printf("s = %d, calls = %d, total = %d\n", s, calls, total);
    return 0;
}
```
```output
s = 3, calls = 2, total = 3
```

换个写法，只要两个实参碰同一个变量，就立刻从"未指定"变成"未定义"：`add2(i++, i++)`。下面这个更隐蔽——`a[i] = i++` 里 `i++` 的副作用和"用 `i` 算下标"这件事没有顺序，所以下标可能是 0 也可能是 1：

```c run id=seq-index-ub expect=UB warnings=allow
#include <stdio.h>

int main(void) {
    int a[8] = { 0 };
    int i = 0;
    for (int k = 0; k < 8; k++) {
        a[i] = i++;               /* 未排序：读 i 算下标，i++ 又改 i */
    }
    printf("i = %d\n", i);
    return 0;
}
```

本平台实测这段代码被判 `UB`，但**抓住它的理由并不是"未排序修改"**，而是 UBSan 的数组越界检查：在 `-O0` 生成的代码里，编译器的取值顺序让 `i` 先涨到 8 再去算下标，`a[8]` 越界了。这个细节说明两件事：一是 UB 的后果可以离肇事的那一行很远；二是工具也有盲区，真正防住这类错误的还是"不要在一条表达式里改两次同一个变量"这条纪律。

安全的改写只有一种思路——**先把旧值取出来放进临时变量，让每条语句只做一件事**：

```c run id=seq-rewrite
#include <stdio.h>

int main(void) {
    int a[8] = { 0 };
    int i = 0;
    for (int k = 0; k < 8; k++) {
        int old = i;              /* 1. 取旧值：只读，不改 */
        i = old + 1;              /* 2. 只做一次修改 */
        a[old] = old;             /* 3. 用临时变量当下标 */
    }
    printf("i = %d, a[0] = %d, a[7] = %d\n", i, a[0], a[7]);
    return 0;
}
```
```output
i = 8, a[0] = 0, a[7] = 7
```

改写之后语义完全确定：每一轮 `old` 都是当时的 `i`，下标和值都是 `old`，与编译器怎么排指令无关。

### 怎么写出不依赖顺序的代码

三条可以当纪律背下来的规则：

1. **一条表达式里，对同一个变量最多改一次**。`i++` 出现两次就不行，无论中间是 `+`、`*` 还是逗号之外的任何东西。
2. **改之前先存旧值**。`a[i] = i++;` 拆成 `int old = i; i = old + 1; a[old] = old;`，把"顺序"变成源码里看得见的语句顺序。
3. **需要顺序就用排序点明写**。`;`、`,`、`&&`、`?:` 是标准点名的排序点；不要指望编译器"自然会先算左边"。

还有一个跨语言的坑：Java 和 C# 都**明确规定了**表达式从左到右求值，所以同一段代码在 Java 里完全确定、在 C 里是 UB。从别的语言转过来的人最容易在这里翻车——"我在 Java 里这么写没问题"不是理由。

最后，`i = i++` 这种写法没有任何实际价值：想自增就写 `i++` 或 `i = i + 1`，两者都有确定语义。**不写 UB 比事后检查 UB 便宜得多**。

## 编译与运行

用 gcc 或 clang 都行，本平台使用 Clang（x86-64 Windows，UCRT）：

```bash
gcc -std=c17 -Wall -Wextra seq.c -o seq
./seq
```

```bash
clang -std=c17 -Wall -Wextra seq.c -o seq
./seq
```

`-Wall` 里已经包含 `-Wunsequenced`，所以 `i = i++`、`a[i] = i++` 这类写法会直接收到警告。想看它到底属于哪个警告组，可以单独打开：

```bash
clang -std=c17 -Wunsequenced seq.c -o seq
```

编译输出会形如：

```text
seq.c:5:11: warning: multiple unsequenced modifications to 'i' [-Wunsequenced]
    5 |     i = i++;
      |         ~ ^
```

想看"两档到底生成了什么"，用 `-S` 对比汇编：

```bash
clang -std=c17 -O0 -S seq.c -o seq-O0.s
clang -std=c17 -O2 -S seq.c -o seq-O2.s
```

`-O0` 下 `i = i++` 会展开成"读 `i` → 存 `i+1` → 存回旧值"好几条指令，`-O2` 下往往被折叠成一两条，甚至整段消失。**汇编不一样，结果却可能一样**——这再次说明"结果一样"不等于"行为有定义"，它只是编译器凑巧选了同一条路。

几个额外开关：

- `-fsanitize=undefined`：本平台的默认配置，但它**抓不到未排序修改**，只能抓到这类 UB 顺带引发的越界、溢出；
- `-Werror=unsequenced`：把这条警告升级成错误，给团队当纪律用；
- `clang --analyze seq.c`：静态分析器，对一部分"读未初始化值/未排序访问"有额外检查。

## 常见错误

### 以为 `i = i++` 是"先自增再赋值" [UB]
这是最常见的误解：把 `i++` 当成"i 变成 i+1，然后把新值赋回去"。实际上 `i++` 的**值**是旧值，赋值写回的也是旧值，而自增那一次写和赋值这一次写之间没有顺序。写成两条语句就清楚了：`i++; i = 5;` 和 `i = 5; i++;` 显然不同，`i = i++;` 正是把这件说不清的事压在了一行里。

### 把"求值顺序未指定"当成"未定义行为" [WA]
`f(g(), h())` 里先算谁标准不管，但两个顺序都合法，结果确定——这是未指定行为，可以放心写（只要两个函数不互相干扰）。反过来，`f(i++, i++)` 因为两次写同一个对象而升级成 UB。把两者混为一谈，会导致两个方向的错误：要么把合法代码当成 bug 去"修"，要么把 UB 当成"顺序问题"去"调"。

### 以为 `-O0` 跑对了就说明代码没问题 [WA]
本平台实测 `i = i++;` 在 `-O0` 和 `-O2` 下都输出 5，看起来"很稳定"。但这份稳定来自编译器实现，不是语言保证：换 GCC、换 Clang 版本、把这段代码挪进另一个函数，结果都可能变。判断依据只能是标准，不能是某次运行的输出。

### 以为 sanitizer 能兜住所有 UB [UB]
`-fsanitize=undefined` 有明确的检查清单（越界、溢出、空指针、对齐、类型转换……），"未排序的修改"不在里面。所以一段含 `i = i++` 的代码可以一路绿灯跑完，同时它仍然是 UB。这类问题要靠 `-Wunsequenced` 警告和人工审查。

### 用逗号运算符"修饰"危险代码 [UB]
`printf("%d %d\n", (i++, 1), i++)` 里加了个逗号，看起来"有顺序了"，其实只是让第一个实参内部的顺序确定，两个实参之间依然没有顺序。排序点只对**它自己的两个操作数**负责，不会传播到外层表达式。

```c run id=seq-err-comma warnings=allow nocheck reason="实参之间仍然没有顺序，输出不确定"
#include <stdio.h>

int main(void) {
    int i = 0;
    printf("%d %d\n", (i++, 1), i++);   /* 错：逗号只管自己那一对操作数 */
    return 0;
}
```

## 客观题

### q-s5-ub-sequence-1 single
下面四段代码里，哪一段**没有**未定义行为（即使它依赖了"未指定"的求值顺序也没关系）？

- [x] `int s = add(note(1), note(2));`，其中 `note` 只往两个独立的全局计数器里累加
  > 正确。两个实参之间没有顺序，所以"先算谁"是未指定的；但两个顺序都不会产生冲突访问（各自写各自的计数器、都只读自己），程序的结果是确定的：`s` 一定是 3。这正是"未指定但合法"的典型样子。
- [ ] `int i = 0; i = i++;`
  > 错。`i++` 的副作用（写 6）和赋值的副作用（写回旧值）都是对 `i` 的写，两者之间没有排序关系，属于"同一对象上两次未排序的修改"，是 UB。本平台实测输出 5，但那只是实现的选择。
- [ ] `int i = 0; int a[3]; a[i] = i++;`
  > 错。算下标要读 `i`，`i++` 又要写 `i`，一读一写未排序，同样是 UB。它的后果可能表现为"下标算错"（本平台在循环版本里就是先越界才被 UBSan 抓住），但根源是未排序访问。
- [ ] `int i = 0; printf("%d %d\n", i++, i++);`
  > 错。函数调用的实参之间没有顺序，两个 `i++` 都写同一个 `i`，属于两次未排序的修改。把 `printf` 换成自己的函数也一样，是否 UB 与"被调用的函数是什么"无关。
