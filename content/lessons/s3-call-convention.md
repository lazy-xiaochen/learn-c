## 讲解

### 调用约定到底约定了三件事
函数调用在 C 语言里只是 `f(a, b)`，但在机器层面它是一份"双方必须都遵守的协议"，协议内容只有三条：

1. **参数放在哪里**：是全部走栈，还是优先用寄存器？第几个参数开始走栈？
2. **返回值放在哪里**：是某个通用寄存器，还是由调用者事先分配一块空间？
3. **谁负责把栈恢复原状**：调用者清理还是被调用者清理？

这三条合起来叫**调用约定**（calling convention）。它不属于 C 标准——标准只说"函数能调用、参数按值传递"，具体怎么传由平台 ABI（应用二进制接口）规定。所以同一份 C 代码在 x86-64 Linux、x86-64 Windows、32 位 x86 上编译出来的调用方式完全不同，这也是"函数指针类型不匹配"能悄悄毁掉程序的原因。

### 参数放在哪里：寄存器优先，放不下才走栈
x86-64 有足够的寄存器，因此前几个整型/指针参数根本不进栈，而是直接放在寄存器里：

| 平台 | 整型/指针参数 | 浮点参数 | 超出部分 |
|---|---|---|---|
| x86-64 System V（Linux/macOS） | rdi, rsi, rdx, rcx, r8, r9（6 个） | xmm0–xmm7 | 从右往左压栈 |
| x86-64 Windows | rcx, rdx, r8, r9（4 个） | xmm0–xmm3 | 从右往左压栈，且调用者要留 32 字节影子空间 |
| 32 位 x86（cdecl） | 没有，全部走栈 | 全部走栈 | 全部压栈 |

参数多的时候，超出的部分还是得走栈。下面这个函数有 8 个 `int` 参数，在 Windows x64 上前 4 个进寄存器、后面 4 个进栈，但它算出来的结果和"全部走栈"完全一样——**调用约定只影响怎么传，不影响语义**：

```c run id=cc-where-args
#include <stdio.h>

/* 8 个 int 参数：前 4 个走寄存器，第 5 个起走栈（Windows x64 的规则） */
static long long sum8(int a1, int a2, int a3, int a4, int a5, int a6, int a7, int a8) {
    return (long long)a1 + a2 + a3 + a4 + a5 + a6 + a7 + a8;
}

int main(void) {
    printf("sum8(1..8) = %lld\n", sum8(1, 2, 3, 4, 5, 6, 7, 8));
    return 0;
}
```
```output
sum8(1..8) = 36
```

在 C 源码里你**看不到**参数究竟落在寄存器还是栈上：`&a1` 拿到的只是编译器为了满足"取地址"而在栈上临时复制的一份。想确认真正的落点，只能用 `clang -S` 看汇编（见「编译与运行」）。

### 为什么参数要从右往左压
32 位 cdecl 时代所有参数都走栈，压栈顺序就成了必须写死的约定：**从右往左**。原因不是习惯，而是为了下面这个性质：

> 最后压入的参数离返回地址最近，于是**第 1 个参数永远位于 `ebp+8`**，与参数个数无关。

这条性质有两个直接好处：

- 被调用者不需要知道自己被传了几个参数，就能按 `ebp+8`、`ebp+12`、`ebp+16` 依次取到第 1、2、3 个参数——函数序言只要 `mov ebp, esp`，参数地址全是编译期常量偏移；
- **变参函数**（`printf`）能工作：格式串是第 1 个参数，永远在 `ebp+8`，之后按格式串里的 `%d`、`%s` 一个个往上读。如果改成从左往右压，第 1 个参数的位置会随实参个数变化，被调用者就无法在编译期定位它。

反过来说，"先压的在最高地址"这一点很容易记反。下面把压栈过程打印出来，注意落点是**越来越低**的：

```c run id=cc-push-order
#include <stdio.h>

int main(void) {
    int arg[3] = { 10, 20, 30 };         /* a, b, c */
    char name[3] = { 'a', 'b', 'c' };
    int offset = 8 + 4 * 3;              /* 参数区最高位置：ebp+16 */

    /* cdecl：从右往左压栈；栈向低地址增长，所以每压一个，落点就比上一个低 4 字节 */
    for (int i = 2; i >= 0; i--) {
        offset -= 4;
        printf("push %c（值 %d）→ 落在 ebp+%d\n", name[i], arg[i], offset);
    }
    printf("被调用者按 ebp+8、ebp+12、ebp+16 取到的就是 a、b、c\n");
    return 0;
}
```
```output
push c（值 30）→ 落在 ebp+16
push b（值 20）→ 落在 ebp+12
push a（值 10）→ 落在 ebp+8
被调用者按 ebp+8、ebp+12、ebp+16 取到的就是 a、b、c
```

调用 `f(10, 20, 30)`、被调用者刚执行完 `push ebp; mov ebp, esp` 时，栈是这样的（地址只是示意，实际每次运行都不同）：

```memory title="32 位 cdecl：f(10, 20, 30) 进入函数体时的栈（地址为示意）"
偏移 | 内容 | 是谁放的 | 说明
ebp+16 | 30 | 调用者 | 第 3 个参数 c：最先压入，所以落点最高
ebp+12 | 20 | 调用者 | 第 2 个参数 b
ebp+8 | 10 | 调用者 | 第 1 个参数 a：最后压入，紧贴返回地址
ebp+4 | 返回地址 | call 指令 | 返回到调用点之后的那条指令
ebp+0 | 调用者的 ebp | 被调用者的 push ebp | 保存上一层的帧指针，返回前 pop 回去
ebp-4 | 临时结果 | 被调用者 | 局部变量从 ebp-4 开始向低地址分配
ebp-8 | 循环变量 i | 被调用者 | 每多一个局部变量，ebp 的偏移再减 4
```

注意 `ebp+0` 存的是**旧的 ebp**，`ebp+4` 才是返回地址——这两个位置是"能找回返回地址"的全部秘密：`call` 先把返回地址压栈，被调用者再把自己的 ebp 压上去，于是返回地址固定落在 `ebp+4`，函数结束时 `leave; ret` 就能准确弹回去。

如果参数超过寄存器数量、走到了 64 位 Windows 的栈上，布局是这样的（32 字节影子空间是给被调用者存寄存器参数用的）：

```memory title="Windows x64：sum8(1..8) 的参数落点（栈地址为示意）"
位置 | 内容 | 是第几个参数 | 说明
rcx | 1 | 第 1 个 | 整型参数依次用 rcx、rdx、r8、r9
rdx | 2 | 第 2 个 | 
r8 | 3 | 第 3 个 | 
r9 | 4 | 第 4 个 | 
rsp+32 | 5 | 第 5 个 | 第 5 个起走栈，偏移 32 就是 32 字节影子空间
rsp+40 | 6 | 第 6 个 | 
rsp+48 | 7 | 第 7 个 | 
rsp+56 | 8 | 第 8 个 | 最后一个参数的落点最高
```

### 返回值怎么带回
返回值也有一套约定，按大小分三种情况：

- **整数、指针、`char`/`short`（提升后）**：放在 `rax`（32 位是 `eax`）；
- **浮点数**：放在 `xmm0`；
- **小的结构体（不超过 16 字节）**：拆成两个 8 字节，分别放 `rax` 和 `rdx`；
- **大的结构体**：放不进寄存器，于是由**调用者**在自己栈上留一块空间，把它的地址当作"隐藏的第 0 个参数"传给被调用者，被调用者直接往那块空间里写。这个隐藏参数叫 sret（structure return）指针。

不管走哪条路，C 语言的语义都是**返回一个值（副本）**，不是返回原来那块内存：

```c run id=cc-return-struct
#include <stdio.h>

typedef struct {
    long long x;
    long long y;
    long long z;
} Vec3;                                  /* 24 字节，超过寄存器能带走的 16 字节 */

static Vec3 make(long long base) {
    Vec3 v = { base, base * 2, base * 3 };
    return v;                            /* 大结构体：调用者提供空间，隐藏指针传进去 */
}

int main(void) {
    Vec3 a = make(10);
    a.x = 999;                           /* 改的是 main 里这份副本 */
    Vec3 b = make(10);
    printf("sizeof(Vec3) = %zu\n", sizeof(Vec3));
    printf("a = %lld %lld %lld\n", a.x, a.y, a.z);
    printf("b = %lld %lld %lld\n", b.x, b.y, b.z);
    return 0;
}
```
```output
sizeof(Vec3) = 24
a = 999 20 30
b = 10 20 30
```

`sret` 的存在解释了初学者常踩的一个坑：**返回大结构体的函数，返回值其实是由调用者准备好空间、被调用者填进去的**，但语法上你仍然拿到一个独立的副本，`a.x = 999` 不会影响 `b`，更不会影响函数里那个已经消失的局部变量 `v`。换句话说，实现细节（隐藏指针）不改变语言的语义（按值返回）。

### 变参函数：参数没有类型信息，全靠格式串
`printf` 这类函数的参数个数和类型都不固定，编译器无法在调用点把它们规整好。C 提供的 `stdarg.h` 让被调用者能**按顺序**一个个取出参数，但前提是它必须知道每个参数是什么类型——这个信息只能由调用者通过格式串告诉它：

```c run id=cc-variadic
#include <stdarg.h>
#include <stdio.h>

/* 变参函数：靠 count 知道有几个参数，靠 va_arg 按类型一个个取 */
static int sum_all(int count, ...) {
    va_list ap;
    va_start(ap, count);
    int total = 0;
    for (int i = 0; i < count; i++) {
        total += va_arg(ap, int);
    }
    va_end(ap);
    return total;
}

int main(void) {
    printf("sum_all(4, 10, 20, 30, 40) = %d\n", sum_all(4, 10, 20, 30, 40));
    return 0;
}
```
```output
sum_all(4, 10, 20, 30, 40) = 100
```

`va_arg(ap, int)` 能正确往前走，靠的就是"参数区是一段连续、按声明顺序排列的存储"这个约定。如果类型写错（比如实际传的是 `double`，却用 `va_arg(ap, int)` 取），指针就会走错位置，读到的全是垃圾——这是**未定义行为**，而不是"自动转换"。

### cdecl 与 stdcall：唯一区别是谁清理栈
32 位 x86 上有两种主流约定，它们的**参数布局完全一样**（都是从右往左压栈、第 1 个参数在 `ebp+8`），唯一的区别是"函数返回后，谁把 `esp` 抬回调用前的位置"：

- **cdecl**（C 的默认约定）：**调用者**清理。每个调用点在 `call` 之后自己加一条 `add esp, N`；
- **stdcall**（Windows API 的 `WINAPI`）：**被调用者**清理。函数的返回指令是 `ret N`，弹回返回地址的同时把 N 字节参数一起弹掉。

```c run id=cc-cleanup
#include <stdio.h>

/* 用"参数区字节数"演示两种约定下 esp 由谁调整回去 */
static void report(const char *conv, int argc) {
    int bytes = argc * 4;
    printf("%s：参数区 %d 字节，", conv, bytes);
    if (conv[0] == 'c') {
        printf("调用者在返回后执行 add esp, %d\n", bytes);
    } else {
        printf("被调用者用 ret %d 自己把 esp 抬高 %d\n", bytes, bytes);
    }
}

int main(void) {
    report("cdecl", 3);
    report("stdcall", 3);
    return 0;
}
```
```output
cdecl：参数区 12 字节，调用者在返回后执行 add esp, 12
stdcall：参数区 12 字节，被调用者用 ret 12 自己把 esp 抬高 12
```

两种约定各有取舍：

| | cdecl | stdcall |
|---|---|---|
| 参数布局 | 从右往左压栈 | 完全相同 |
| 谁清理栈 | 调用者（每个调用点一条 `add esp, N`） | 被调用者（`ret N`） |
| 代码体积 | 调用点多时更大 | 更小 |
| 支持变参 | 支持 | **不支持**（被调用者不知道自己该弹多少字节） |
| 名字修饰 | `_add` | `_add@8`（@ 后面是参数字节数） |
| 典型用途 | C 的默认约定 | Windows API、回调函数 |

最后一行"名字修饰"很关键：两种约定的函数在目标文件里的符号名不同，所以**声明和定义用了不同约定时，链接器会直接报"找不到符号"**——这是好事，错误在链接期就暴露了。真正危险的是函数指针：把一个 `__stdcall` 函数的地址赋给 `__cdecl` 的函数指针，类型检查通不过，强行转换后调用就会让栈失衡。

到了 x86-64，**这两种约定被合并了**：Windows x64 只有一种调用约定，`__cdecl`、`__stdcall`、`__fastcall` 这些关键字仍然能写（为了源码兼容），但编译器会忽略它们。所以下面这种写法在 64 位下"能编译、没效果"，不要指望它改变任何东西：

```c
#if defined(_WIN32) && defined(__i386__)
#define CC_CDECL   __cdecl
#define CC_STDCALL __stdcall
#else
#define CC_CDECL
#define CC_STDCALL          /* 64 位下为空：写不写都一样 */
#endif
```

### 参数求值顺序：标准没有规定
这里有一个必须和"压栈顺序"区分开的概念：**实参的求值顺序**。标准只保证"所有实参都在函数体开始执行前求值完毕"，但**没有规定谁先谁后**。下面用两个带副作用的函数把实际顺序记录下来：

```c run id=cc-eval-order
#include <stdio.h>

static int log[4];
static int steps;

static int note(int v) {
    log[steps++] = v;
    return v;
}

static int add3(int a, int b, int c) {
    return a + b + c;
}

int main(void) {
    int sum = add3(note(1), note(2), note(3));
    printf("sum = %d，实际求值顺序：", sum);
    for (int i = 0; i < steps; i++) {
        printf("%s%d", i ? " → " : "", log[i]);
    }
    printf("\n");
    return 0;
}
```
```output
sum = 6，实际求值顺序：1 → 2 → 3
```

这块输出是**本平台 Clang 的实测结果**（从左到右），但标准并不保证：换编译器、换优化级别，完全可能变成 `3 → 2 → 1`。因此这类代码不能作为"知识"记住，只能作为"不要依赖"的警告。和它相关的一条硬规则是：**同一个表达式里对同一个变量做两次未排序的修改是未定义行为**，例如 `f(i++, i++)`，编译器可以生成任何结果。

把三个概念排一排，别再混：

1. **求值顺序**：先算哪个实参——标准未规定；
2. **压栈顺序**：参数以什么次序进入栈——cdecl 规定从右往左；
3. **内存布局**：参数最终落在哪个地址——由前两条和栈增长方向共同决定，第 1 个参数在 `ebp+8`。

### 调用约定不一致会发生什么
如果在同一个程序里出现了两份"对同一个函数的不同理解"，后果分三档：

- **链接期发现**：名字修饰不同（`_add` vs `_add@8`）→ 报未定义符号，最幸运；
- **运行期栈失衡**：调用者以为被调用者会清理、被调用者以为调用者会清理，`esp` 就永久偏移了 N 字节。接下来任何一次 `ret` 都可能跳到垃圾地址，表现为莫名其妙的崩溃（本平台判 `RE`）；
- **悄悄读错参数**：64 位下参数走寄存器，类型写错时不一定崩，而是算出一个看似合理的错值（`WA`）。

所以调用约定相关的 bug 有个共同特征：**错误不在出错的那一行**。看到"函数调用后崩溃"或"返回值莫名其妙"，要回头检查函数指针的类型、头文件里的声明、以及是否把 32 位时代的约定假设带到了 64 位。

## 编译与运行

用 gcc 或 clang 编译都行，本平台使用 Clang（x86-64 Windows，UCRT）：

```bash
gcc -std=c17 -Wall -Wextra call.c -o call
./call
```

```bash
clang -std=c17 -Wall -Wextra call.c -o call
./call
```

想看参数到底落在寄存器还是栈上，用 `-S` 生成汇编再读一眼：

```bash
clang -std=c17 -O0 -S call.c -o call.s
```

编译 `sum8(1, 2, 3, 4, 5, 6, 7, 8)` 的调用点，汇编大致是（本平台实测，只保留关键行）：

```asm
	movl	$1, %ecx          # 第 1 个参数走寄存器
	movl	$2, %edx          # 第 2 个
	movl	$3, %r8d          # 第 3 个
	movl	$4, %r9d          # 第 4 个
	movl	$5, 32(%rsp)      # 第 5 个起走栈，32 是影子空间的大小
	movl	$6, 40(%rsp)
	movl	$7, 48(%rsp)
	movl	$8, 56(%rsp)
	callq	sum8
```

被调用者内部的函数序言和返回值也能对照着看：

```asm
sum8:
	subq	$16, %rsp         # 给局部变量留空间
	movl	%ecx, 12(%rsp)    # 把寄存器参数存到栈上（因为要取地址/统一处理）
	movl	%edx, 8(%rsp)
	...
	movq	%rax, %rdx        # 返回值在 rax，printf 之前挪到 rdx
```

几点说明：

- 加 `-O2` 之后，参数可能整个留在寄存器里，连 `subq $16, %rsp` 都消失，栈上什么都看不到——**优化会改变布局**，所以不要靠"读汇编数偏移"来写程序逻辑；
- 在 Linux（System V ABI）上，前 6 个整型参数依次用 `rdi`、`rsi`、`rdx`、`rcx`、`r8`、`r9`，和 Windows 的前 4 个不同。同一份代码跨平台移植时，只有"参数个数超过寄存器数量"的部分才会真正上栈；
- 想看 C 语言层面的行为，用 `-fsanitize=undefined` 编译：类型不匹配的变参调用、越界的 `va_arg` 都可能被 UBSan 抓住。

## 常见错误

### 以为参数按声明顺序从低地址到高地址排列 [WA]
栈向低地址增长，而参数从右往左压，两个方向叠加的结果是：**第 1 个参数在最低的偏移（`ebp+8`），最后声明、最先压入的参数反而在最高地址**。把顺序记反，推算出来的偏移会整体镜像，多参数函数一取就错。

### 以为"求值顺序"和"压栈顺序"是一回事 [WA]
`f(g(), h())` 里先算 `g` 还是先算 `h`，标准没有规定；但无论谁先算，结果都要按 `cdecl` 的规则从右往左压栈。把这两件事混在一起，就会写出"本机跑得对、换编译器就错"的代码——尤其是依赖 `g()`、`h()` 修改同一个全局变量的程序。

### 在 64 位程序里用 `__stdcall` 想改变调用方式 [WA]
x86-64 Windows 只有一种调用约定，`__cdecl` / `__stdcall` / `__fastcall` 会被编译器静默忽略：代码照常编译、照常运行，你以为自己换了约定，其实什么都没变。这类代码在 32 位下才会真正生效，跨平台时行为会突然改变。

### 以为函数返回的结构体和函数里那个局部变量是同一块内存 [WA]
返回大结构体时，底层确实用了"调用者提供空间 + 隐藏指针"的 sret 机制，但语言层面返回的是**副本**：函数里的 `v` 在 `return` 之后就随栈帧一起消失了。

```c run id=cc-err-struct-copy
#include <stdio.h>

typedef struct {
    int x;
    int y;
} Pair;

static Pair make(int x, int y) {
    Pair p = { x, y };
    return p;                    /* 返回的是 p 的副本 */
}

int main(void) {
    Pair a = make(1, 2);
    Pair b = a;                  /* 又一次复制 */
    b.x = 100;
    printf("a.x = %d, b.x = %d\n", a.x, b.x);
    return 0;
}
```
```output
a.x = 1, b.x = 100
```

想真正共享一份数据，必须传指针（`Pair *`），而不是靠返回值。

### 以为变参函数的类型可以"自动转换" [UB]
`printf("%d", x)` 里 `%d` 要求一个 `int`，而变参调用**不做类型检查**：`double`、`long long` 都不会被自动转成 `int`，只会被原样放进参数区，然后被 `%d` 按 4 字节读出来。结果要么是垃圾值，要么读到相邻参数，属于未定义行为。变参函数必须严格按实际类型写格式符（`%f` 对应 `double`，`%lld` 对应 `long long`）。

## 客观题

### q-s3-call-convention-1 single
32 位 x86 的 cdecl 约定下调用 `int f(int a, int b, int c)`，实参从右往左压栈。被调用者执行完 `push ebp; mov ebp, esp` 之后，关于参数位置的说法哪一个是正确的？

- [x] `a` 在 `ebp+8`，`b` 在 `ebp+12`，`c` 在 `ebp+16`
  > 正确。`c` 最先压入，落在最高地址；`a` 最后压入，紧贴 `call` 压进来的返回地址（`ebp+4`），所以从 `ebp+8` 开始依次是 `a`、`b`、`c`。这正是"第 1 个参数位置固定"的来源，也是变参函数能靠格式串顺序读取参数的前提。
- [ ] `a` 在 `ebp+16`，`b` 在 `ebp+12`，`c` 在 `ebp+8`
  > 错。这个排法对应"参数按声明顺序从左往右压栈"，但 cdecl 是从右往左压；栈向低地址增长，先压的 `c` 落在更高的地址上，所以 `c` 不可能在 `ebp+8`。
- [ ] 三个参数全部通过寄存器传递，栈上没有参数
  > 错。寄存器传参是 x86-64 的规则；32 位 x86 的 cdecl 没有可用的参数寄存器，三个参数都在栈上。即使换成 x86-64，也要看具体 ABI：System V 用 6 个寄存器，Windows x64 只用 4 个。
- [ ] 改成 stdcall 之后，压栈顺序会反过来，`a` 会落在 `ebp+16`
  > 错。stdcall 和 cdecl 的唯一区别是**谁清理栈**：cdecl 由调用者 `add esp, N`，stdcall 由被调用者 `ret N`。两者的参数布局完全一样，`a` 仍然在 `ebp+8`。stdcall 不支持变参，正是因为被调用者拿不到参数个数、无法算出 `ret N` 里的 N。
