## 讲解

### 局部变量不会自动清零
Java、Python 里的局部变量默认是 0 或 `None`，C 不是。函数里声明的局部变量（自动存储期）只做了"分配空间"这一件事，**里面的内容就是那块栈内存上一次被使用时留下的字节**。函数调用层次一变，那块内存的"残留物"就变了，于是同一个变量在同一份代码里可以有无数个值。

这类值有个形象的叫法：**垃圾值**。它既不是"随机的"（同一个程序连续跑两次，往往是同一个值），也不是"稳定的"（换个优化级别、换台机器就变），更不是"0"。

会产生未初始化值的地方比想象中多：

| 位置 | 是否自动清零 | 说明 |
|---|---|---|
| 局部变量 `int x;` | 否 | 栈上的残留字节 |
| 局部数组 `int a[10];` | 否 | 只写了 `a[0]`、`a[1]`，其余仍是残留字节 |
| `malloc` 得到的内存 | 否 | 堆上的残留字节 |
| `calloc` 得到的内存 | **是** | 标准保证全部字节为 0 |
| 全局变量 / `static` 变量 | **是** | 程序启动时清零（BSS 段） |
| 结构体 `struct S s;` | 否 | 逐个成员赋值前，未赋值的成员是垃圾值 |

所以"运气好"这件事是有规律的：全局变量和 `static` 变量恰好是 0，`calloc` 恰好是 0，这让很多人形成"C 会自动清零"的错觉；一到局部变量和 `malloc`，同样的写法立刻出问题。

### 为什么"读未初始化"是 UB，而不只是"值不确定"
初学者常把这件事理解成"值是随机的，那我多试几次、取个常见值"。标准的态度要严厉得多：

- C17 6.2.6.1 说，某些对象表示（trap representation）根本不对应任何值；
- 6.3.2.1 规定，读取一个"未初始化的自动存储期对象"的值是**未定义行为**（`unsigned char` 是例外）；
- 一旦这次读取是 UB，整个程序就失去保证——不只是"这个值不好说"。

为什么标准要这么严格？因为**允许编译器假设"变量在第一次读取前已经被写过"**，能省掉很多工作：寄存器分配、消除冗余读写、把变量整体放进寄存器。如果未初始化读只是"值不确定"，编译器就必须在每次读取前加载真实内存，优化会大幅受限。

代价是：一旦代码里真的读了未初始化变量，编译器的优化就变成了"基于错误前提的推理"，结果无法预测。下面这个函数就是例子：

```c run id=un-o0 opt=-O0 warnings=allow nocheck reason="读取未初始化的 x，值的具体内容取决于栈上的残留字节"
#include <stdio.h>

static int classify(void) {
    int x;                       /* 没有初始化 */
    if (x == 0) {
        return 1;
    }
    if (x != 0) {
        return 2;
    }
    return 3;
}

int main(void) {
    printf("classify = %d\n", classify());
    return 0;
}
```

从逻辑上看，`x` 要么等于 0、要么不等于 0，`return 3` 永远走不到。但 `x` 未初始化，两次读取之间标准不保证读到同一个值，编译器完全可以认为"两条路都可能不成立"。`-O0` 下它按字面执行，本平台打印出 `classify = 2`；换到 `-O2`，同一份代码被编译成一条非法指令：

```c run id=un-o2 opt=-O2 warnings=allow expect=RE
#include <stdio.h>

static int classify(void) {
    int x;                       /* 没有初始化 */
    if (x == 0) {
        return 1;
    }
    if (x != 0) {
        return 2;
    }
    return 3;
}

int main(void) {
    printf("classify = %d\n", classify());
    return 0;
}
```

`-O2` 的推理是：两次条件判断用的是同一个"不确定值"，若第一次为假、第二次也为假，就说明 `x` 既不等于 0 又不不等于 0——不可能。于是 `return 3` 这条路径被判定为"不可达"，编译器在那里放了一条 `ud2`（非法指令）。程序以 `0x80000003`（断点指令）终止，判 `RE`。

**同一份代码：`-O0` 打印一个数，`-O2` 直接崩溃。** 这不是编译器在捣乱，而是"读未初始化值"这个 UB 被利用的两种合法表现。注意两次都不是"正确答案"——这个函数本来就没有正确答案。

### 未初始化数组：`-Wall` 也未必提醒
比局部标量更隐蔽的是"只填了一部分"的数组。下面这段代码只给 `a[0]`、`a[1]` 赋了值，却把 4 个元素全打印出来：

```c run id=un-partial warnings=allow nocheck reason="a[2]、a[3] 从未赋值，打印出来的是栈上的残留字节"
#include <stdio.h>

int main(void) {
    int a[4];
    a[0] = 1;
    a[1] = 2;
    printf("%d %d %d %d\n", a[0], a[1], a[2], a[3]);
    return 0;
}
```

本平台这次打印出 `1 2 0 0`，看起来"没赋值的元素是 0"——但那只是这块栈内存刚好是 0。同一份代码在函数被多层调用之后再执行，`a[2]` 就可能是上一个函数留下的任何字节。这种"看起来是 0"的巧合极其危险，因为它会让测试全部通过。

`-Wall -Wextra` 对**局部标量**通常会给警告：

```
warning: variable 'x' is uninitialized when used here [-Wuninitialized]
```

但对"数组元素只写了一部分""结构体成员只赋了一部分""通过指针传出去的缓冲区"这几类，编译器基本不作声。所以**零警告 ≠ 没有未初始化问题**，这一点和越界、溢出是一样的。

### 正确的写法：让每个变量在读取前都有值
结论很短：**声明时就初始化，或者保证第一次读取之前一定已经赋值**。三种最常见的场景，各给一个"一定正确"的版本。

第一种，累加器和最值。累加器从 0 开始；最值用**第一个元素**做初值，而不是猜一个"足够大/足够小"的哨兵：

```c run id=un-init-accum
#include <stdio.h>

int main(void) {
    int values[5] = { 3, -1, 7, 0, 5 };
    int sum = 0;                        /* 累加器从 0 开始 */
    int max = values[0];                /* 用第一个元素做初值，不用猜哨兵 */
    int min = values[0];
    for (int i = 0; i < 5; i++) {
        sum += values[i];
        if (values[i] > max) {
            max = values[i];
        }
        if (values[i] < min) {
            min = values[i];
        }
    }
    printf("sum = %d, max = %d, min = %d\n", sum, max, min);
    return 0;
}
```
```output
sum = 14, max = 7, min = -1
```

第二种，数组。`int a[4] = { 0 };` 会把**所有**元素清零（只写 `{ 0 }` 时，剩下的元素按 0 初始化），这样"只填前面几个"也不会读到垃圾值：

```c run id=un-zero-array
#include <stdio.h>

int main(void) {
    int a[4] = { 0 };                   /* 全部清零，后面只赋值前两个也安全 */
    a[0] = 1;
    a[1] = 2;
    int sum = 0;
    for (int i = 0; i < 4; i++) {
        sum += a[i];
    }
    printf("sum = %d, a[3] = %d\n", sum, a[3]);
    return 0;
}
```
```output
sum = 3, a[3] = 0
```

第三种，堆内存。`malloc` 不清零，`calloc` 清零——需要"一开始全是 0"就用 `calloc`，或者 `malloc` 之后自己 `memset`：

```c run id=un-calloc
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int *p = calloc(4, sizeof *p);       /* calloc 保证全部字节为 0 */
    if (p == NULL) {
        return 1;
    }
    printf("calloc 之后：%d %d %d %d\n", p[0], p[1], p[2], p[3]);
    p[0] = 7;
    printf("写入 p[0] 之后：%d %d\n", p[0], p[1]);
    free(p);                             /* 谁申请谁释放 */
    return 0;
}
```
```output
calloc 之后：0 0 0 0
写入 p[0] 之后：7 0
```

## 编译与运行

先按"警告全开"编译，看编译器能不能替你发现：

```bash
gcc -std=c17 -Wall -Wextra -Wuninitialized -Wmaybe-uninitialized un.c -o un
./un
```

```bash
clang -std=c17 -Wall -Wextra -Wuninitialized un.c -o un
./un
```

需要注意的是，**未初始化读没有任何 sanitizer 能在运行期稳定抓住**：ASan 管的是越界和悬垂指针，UBSan 管的是溢出、空指针、非法移位。MSan（MemorySanitizer）专门做这件事，但本平台没有启用它。所以这类 bug 只能靠编译警告、代码习惯和测试用例来防。

想看"垃圾值"有多不稳定，就对照两个优化级别：

```bash
clang -std=c17 -O0 un.c -o un0 && ./un0
clang -std=c17 -O2 un.c -o un2 && ./un2
```

两次输出不一样，几乎可以肯定是未初始化读；如果 `-O2` 直接把程序变成非法指令（像上面的 `classify`），也别惊讶——那同样是 UB 的合法表现。

有一种"查找未初始化读"的土办法：在调试构建里先把栈填上特征值。例如声明一个大的局部数组并写入 `0xAA`，再调用可疑函数，残留字节就更容易被认出来。它不能替代工具，但能帮你确认"这个值确实来自未初始化的栈"。

## 常见错误

### 只给数组的前几个元素赋值
"数组没赋值的部分是 0"是最普遍的错觉。局部数组不会清零，`int a[10];` 里的 10 个元素全是垃圾值；只写 `a[0]`、`a[1]` 就去读 `a[2]`，读到什么完全看栈上原来有什么。

```c
int a[4];
a[0] = 1;
a[1] = 2;
printf("%d\n", a[2]);       /* UB：a[2] 从未赋值 */
```

### 以为 `malloc` 会把内存清零
`malloc` 只负责"给我一块 n 字节的内存"，不负责内容；`calloc` 才会清零。需要清零时用 `calloc(n, sizeof *p)`，或者 `malloc` 之后 `memset(p, 0, n * sizeof *p)`。

```c
int *p = malloc(n * sizeof *p);
printf("%d\n", p[0]);       /* UB：malloc 的内存没有初始化 */
```

### 靠 `-Wall` 兜底
编译器只能分析它能看见的路径。经过函数调用、指针传递、数组下标之后，未初始化读往往一声不响。零警告只能说明"编译器没看出来"，不能说明"代码没问题"。

### 在循环里漏掉某个分支的赋值
`int best;` 配合 `if (a[i] > best) best = a[i];` 是典型的"初值缺失"：第一轮比较时 `best` 还是垃圾值，如果垃圾值恰好很大，最大值就永远更新不了。正确做法是用第一个元素做初值，或者在声明时给一个明确的哨兵值。

```c
int best;                        /* 错：没初始化 */
for (int i = 0; i < n; i++) {
    if (a[i] > best) {           /* 第一次比较用的是垃圾值 */
        best = a[i];
    }
}
```

### 声明了一堆变量却只初始化一部分
`int n, sum, count;` 这种一行声明多个变量的写法很容易漏。`count` 忘了置 0 就直接 `count++`，同样是读未初始化值。声明时就写 `int n = 0, sum = 0, count = 0;` 最省心。

## 客观题

### q-s5-ub-uninit-1 single
关于"读取未初始化的局部变量"，下面哪一种说法是正确的？

- [x] 它是未定义行为：局部变量不会自动清零，值来自栈上的残留字节；编译器可以假设"变量在读取前已被写过"，所以 `-O0` 与 `-O2` 可能给出完全不同的结果
  > 正确。C17 6.3.2.1 规定读取未初始化的自动存储期对象是 UB（`unsigned char` 除外）。局部变量所在的栈空间不会清零，里面是上一次使用留下的字节；而编译器被允许假设"第一次读取前已经写过"，于是同一个函数在 `-O0` 下打印一个数、在 `-O2` 下可能被优化成非法指令。
- [ ] 它只是"值不确定"，多运行几次取出现次数最多的值就是真实结果
  > 错。这不是"未指定行为"（在若干合法结果里选一个），而是 UB：标准不做任何要求，程序整体失去保证。所谓"垃圾值"只是这一次栈上的残留字节，换优化级别、换调用层次都会变，没有"真实结果"可以统计。
- [ ] 局部数组没赋值的元素一定是 0，只有局部标量才是垃圾值
  > 错。局部数组同样不会清零。`int a[10];` 的 10 个元素全是残留字节，只是"只写了前两个、读第三个"这种错误经常发生在小规模测试里，碰巧栈内存是 0 就以为没问题——换成被别的函数用过的栈就会读到完全不同的值。
- [ ] `malloc` 得到的内存会被清零，所以只有栈上的变量需要初始化
  > 错。`malloc` 不清零，`calloc` 才清零。`malloc` 返回的内存里是堆上原有的字节，直接读同样是 UB。需要零初始化时用 `calloc`，或者 `malloc` 之后自己 `memset`。
