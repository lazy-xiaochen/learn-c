## 讲解

### 先看一段"完全正常"的程序
下面这段代码想给二维数组的第一行"补一个元素"。`grid[0]` 只有 3 个 `int`，写 `grid[0][3]` 是越界的，但程序不报错、不崩溃，还打印出了看得懂的结果：

```c run id=ubi-runs sanitize=off
#include <stdio.h>

int main(void) {
    int grid[2][3] = { { 1, 2, 3 }, { 4, 5, 6 } };
    int i = 3;                      /* 用变量做下标，避开编译器的编译期越界检查 */

    printf("before: %d %d %d / %d %d %d\n", grid[0][0], grid[0][1], grid[0][2], grid[1][0], grid[1][1], grid[1][2]);
    grid[0][i] = 99;                /* 越界写：grid[0] 只有下标 0、1、2 */
    printf("after : %d %d %d / %d %d %d\n", grid[0][0], grid[0][1], grid[0][2], grid[1][0], grid[1][1], grid[1][2]);
    return 0;
}
```
```output
before: 1 2 3 / 4 5 6
after : 1 2 3 / 99 5 6
```

`grid[1][0]` 从 4 变成了 99，而 `grid[0]` 的三个元素一个都没变——**越界写没有落在"数组外面"，而是落进了同一块内存里的下一个元素**。对编译器来说这不是"错误"，只是你在它没承诺的地方动了内存。

换一个编译选项，同一段代码会立刻被抓住。本平台的判题器开启了 AddressSanitizer + UndefinedBehaviorSanitizer，`grid[0][i]` 会被 UBSan 的数组边界检查拦下来：

```c run id=ubi-caught expect=UB
#include <stdio.h>

int main(void) {
    int grid[2][3] = { { 1, 2, 3 }, { 4, 5, 6 } };
    int i = 3;

    printf("before: %d %d %d / %d %d %d\n", grid[0][0], grid[0][1], grid[0][2], grid[1][0], grid[1][1], grid[1][2]);
    grid[0][i] = 99;
    printf("after : %d %d %d / %d %d %d\n", grid[0][0], grid[0][1], grid[0][2], grid[1][0], grid[1][1], grid[1][2]);
    return 0;
}
```

两块代码一个字都不差，结局却一个是"结果正常"、一个是"未定义行为"。这说明一个关键事实：**"能跑" 与 "正确" 之间没有因果关系**。能跑只说明"这一次、这个编译器、这个优化级别、这块内存恰好没出事"。

### 标准怎么说：未定义行为就是"不做任何要求"
C17 标准第 3.4.3 节对**未定义行为**（undefined behavior，UB）的定义是：

> behavior, upon use of a nonportable or erroneous program construct or of erroneous data, for which this International Standard imposes no requirements

翻成一句话：**标准对这段代码不提出任何要求**。"不提出要求"不是"结果随机"，而是连"程序会继续运行""会有输出""会崩溃"都不保证。标准允许的具体表现包括（注意最后一条）：

- 什么都不发生，输出看起来完全正确；
- 得到一个莫名其妙但每次运行都一样的值；
- 写坏了别的变量，程序在后面某处才崩；
- 直接崩溃、被操作系统杀掉；
- 或者——最气人的——**每次运行的结果不同**。

任何声称"这段代码在本机跑出来是 X，所以结果是 X"的推理，在 UB 面前都是无效的：你观测到的只是"编译器这一次的选择"，不是语言规定的语义。

下面这段代码演示"看起来最无害"的一类 UB —— 有符号整数溢出。`INT_MAX` 是 `int` 能表示的最大值，再 `+ 1` 就超出了表示范围：

```c run id=ubi-overflow expect=UB
#include <stdio.h>
#include <limits.h>

int main(void) {
    int x = INT_MAX;
    x = x + 1;                       /* UB：有符号整数溢出 */
    printf("x = %d\n", x);
    return 0;
}
```

UBSan 会明确指出越界发生在哪一行、哪个运算、结果为什么无法表示。注意它抓住的是**运算本身**，而不是"结果错了"——在 UBSan 眼里，这一行根本不允许执行。

### 未定义、未指定、实现定义：三种"标准没说死"要分清
初学者常把三件事混成一个"不确定"。它们的性质完全不同：

| 类型 | 标准的态度 | 典型例子 | 能不能依赖 |
|---|---|---|---|
| **未定义行为**（UB） | 不做任何要求，程序整体失去意义 | 数组越界、有符号溢出、空指针解引用、读未初始化变量 | 绝对不能 |
| **未指定行为**（unspecified） | 允许若干种做法之一，**不要求写进文档**，但每次都得是其中之一 | 函数实参的求值顺序、`printf("%d %d", f(), g())` 里先算谁 | 不能依赖具体哪一个 |
| **实现定义行为**（implementation-defined） | 必须选一种做法，而且**必须写进编译器文档** | `sizeof(long)`、`char` 默认是否有符号、负数右移 | 可以查文档后依赖，但换平台要看 |

未指定行为至少还"在几种合法结果里"，UB 连这个保证都没有；实现定义行为则是"合法的、有文档的差异"。三者的分界线是：**标准有没有给出一个必须落在其中的结果集合**。

"实现定义"能正常跑，而且结果稳定：

```c run id=ubi-impl
#include <stdio.h>

int main(void) {
    printf("sizeof(long) = %zu\n", sizeof(long));                 /* 实现定义：本平台 4 */
    printf("char 有默认符号吗：(char)-1 < 0 为 %d\n", (char)-1 < 0); /* 实现定义：本平台 1（有符号） */
    printf("-1 >> 1 = %d\n", -1 >> 1);                            /* 实现定义：本平台算术右移，得 -1 */
    return 0;
}
```
```output
sizeof(long) = 4
char 有默认符号吗：(char)-1 < 0 为 1
-1 >> 1 = -1
```

这四行里没有 UB：结果虽然"因平台而异"，但每个平台都必须给出一个固定答案，而且你可以去查文档确认。所以它们是**可移植性**问题，不是正确性问题。UB 才是"程序从此不受语言保护"。

### 编译器为什么敢假设 UB 不会发生
这是本阶段最重要的一句话：

> 因为 UB 发生时的行为"不做任何要求"，所以**一段出现了 UB 的程序，本来就没有"正确结果"可言**。编译器于是可以反过来假设：**我优化的这段程序是合法的，UB 不会发生**，并在这个前提下做代数化简、删除分支、删除循环。

这个假设不是偷懒，而是标准给的许可：如果优化后的行为和"你期望的行为"不一致，那说明原程序里本来就藏着 UB，编译器并没有违约。

拿 `x * 2 / 2` 举例。数学上它等于 `x`，但这个变形只在"`x * 2` 不溢出"时成立。有符号溢出是 UB，于是编译器可以直接按"不溢出"来化简——先看 `-O0`（老老实实先乘后除）：

```c run id=ubi-algebra-o0 opt=-O0 sanitize=off
#include <stdio.h>
#include <limits.h>

int main(void) {
    volatile int x = INT_MAX;        /* volatile：不许把 x 的读取折叠成常量 */
    int y = x * 2 / 2;
    printf("x = %d\n", (int)x);
    printf("x * 2 / 2 = %d\n", y);
    return 0;
}
```
```output
x = 2147483647
x * 2 / 2 = -1
```

`-O0` 真的先算 `x * 2`：`2147483647 * 2` 溢出成 `-2`，再除以 2 得 `-1`。现在换成 `-O2`，同一份代码：

```c run id=ubi-algebra-o2 opt=-O2 sanitize=off
#include <stdio.h>
#include <limits.h>

int main(void) {
    volatile int x = INT_MAX;        /* volatile：不许把 x 的读取折叠成常量 */
    int y = x * 2 / 2;
    printf("x = %d\n", (int)x);
    printf("x * 2 / 2 = %d\n", y);
    return 0;
}
```
```output
x = 2147483647
x * 2 / 2 = 2147483647
```

同一行 `x * 2 / 2`，`-O0` 得到 `-1`，`-O2` 得到 `2147483647`。两个结果都不是"标准规定的"——标准对溢出后的行为不做要求，`-O2` 只是把 UB 当成"不可能发生"，于是把 `*2` 和 `/2` 一起消掉了。

这条规律可以推广成一句口诀：**`-O0` 执行你写的代码，`-O2` 执行"编译器证明等价"的代码，而证明的前提是你的代码没有 UB。**

### 同一段 UB 的四种典型结局
把"能跑"当成"正确"的人，通常只见过第一种结局：

| 结局 | 现象 | 为什么危险 |
|---|---|---|
| 静默算错 | 输出一个合法但错误的值 | 测试用例不覆盖就永远发现不了 |
| 悄悄改坏别的数据 | 相邻变量、返回地址被覆盖 | 出错点与崩溃点相距很远，难查 |
| 直接崩溃 | 段错误、非法指令、sanitizer 报错 | 反而是最幸运的一种：错误立刻暴露 |
| 看起来完全正确 | 和预期一模一样 | 换编译器/换优化级别/换机器就变，且无法复现 |

第四种最坑：它让"这段代码没问题"这个结论显得有证据。真正的证据只有一个——**代码在标准保证的范围内，且被边界用例验证过**。

### 把 UB 变成可观测的错误
既然 UB 的本质是"失去保证"，工程上的做法就是给代码装探测器：

1. **编译期**：`-Wall -Wextra` 能抓到一部分（未初始化、可疑的越界常量下标、格式串不匹配），但抓不到大部分 UB；
2. **运行期**：`-fsanitize=address,undefined` 让编译器往代码里插检查——越界、溢出、空指针、非法移位等；本平台判题器就是用它把 UB 变成 `UB` / `RE` 判定；
3. **测试**：专门准备边界用例（空输入、`n = 0`、`INT_MAX`、下标恰好等于长度、`NULL` 返回值），这些才是 UB 的高发区；
4. **习惯**：初始化每个变量、访问前判界、指针先判空、溢出前检查——把 UB 挡在发生之前。

需要提醒的是，sanitizer 也不是万能的：严格别名违反、`i = i++` 这类求值顺序问题，ASan 和 UBSan 都抓不到。**抓不到不等于合法**，只是这一次没被观测到。

## 编译与运行

本平台使用 Clang（x86-64 Windows，UCRT）。写代码时先按"零警告"编译：

```bash
gcc -std=c17 -Wall -Wextra ub.c -o ub
./ub
```

```bash
clang -std=c17 -Wall -Wextra ub.c -o ub
./ub
```

想让 UB 现形，加上 sanitizer（`-fno-sanitize-recover=all` 表示第一次出错就终止，而不是打印后继续跑）：

```bash
clang -std=c17 -Wall -Wextra -g -fsanitize=address,undefined -fno-sanitize-recover=all ub.c -o ub
./ub
```

两种优化级别对照着跑，是发现 UB 最省力的办法：

```bash
clang -std=c17 -O0 ub.c -o ub0 && ./ub0
clang -std=c17 -O2 ub.c -o ub2 && ./ub2
```

如果两次输出不一样，先别怀疑"编译器有 bug"，先怀疑代码里有 UB——这是最可靠的信号。想看 `-O2` 到底把哪一行消掉了，用 `-S` 生成汇编再对照：

```bash
clang -std=c17 -O2 -S ub.c -o ub.s
```

本平台判定结果的对应关系是：UBSan 报告 → `UB`；ASan 报告（越界读写、野指针、重复释放）→ `RE`；程序带着非零退出码结束 → `RE`；输出与期望不符 → `WA`。所以"这段代码在本地能跑"和"这段代码能通过判题"是两件独立的事。

## 常见错误

### 把"本机跑出来的结果"当成标准答案
UB 的观测结果依赖编译器版本、优化级别、栈布局甚至环境变量。同一份代码换台机器就可能输出别的值——它从来不是"答案"，只是一次采样。

### 以为加了 `-O0` 就安全
`-O0` 只是"少做优化"，不是"关闭 UB"。越界写在 `-O0` 下照样会改坏相邻变量，读未初始化变量照样是 UB。优化级别只改变"UB 被暴露的方式"，不改变"UB 是 UB"这个事实。

### 把"未指定"当成"未定义"，或者反过来
实参求值顺序是**未指定**（一定在几种合法顺序里），`i = i++` 是**未定义**（标准不做任何要求），`sizeof(long)` 是**实现定义**（有文档、可查询）。把三者混为一谈，就会写出"反正是随机的，无所谓"的代码，或者反过来把能依赖的东西也当成不能依赖。

### 用 `-Wall` 通过来证明"没有 UB"
`-Wall -Wextra` 一个警告都没有，也只说明编译器没看出可疑写法。数组越界、有符号溢出、空指针解引用在很多时候是**运行时**才能确定的，编译器管不了。零警告是底线，不是正确性证明。

```c
int a[3] = { 1, 2, 3 };
int i = 3;
a[i] = 0;              /* -Wall -Wextra 零警告，但这是 UB */
```

## 客观题

### q-s5-ub-intro-1 single
关于"未定义行为（UB）"，下面哪一种说法是正确的？

- [x] 标准对发生 UB 的程序不提出任何要求，编译器可以假设 UB 不会发生并据此优化，所以"本机跑出了正确结果"不能证明代码正确
  > 正确。C17 3.4.3 的原文是"imposes no requirements"。正因为没有任何要求，"程序继续运行并输出正确结果"也只是众多可能之一；编译器更有权在"UB 不会发生"的前提下做代数化简、删除分支。因此观测到的结果不构成正确性证据，只有"在标准保证范围内 + 边界用例通过"才算。
- [ ] UB 就是"结果随机"，只要多跑几次取出现次数最多的那个值就能确定真实结果
  > 错。UB 不是"随机数"：它的表现包括"结果固定但错误""改坏别的变量""崩溃""看起来完全正确"，没有"真实结果"这种东西可供统计。多次运行只能采样到编译器这一次的选择，换优化级别结果就可能完全不同。
- [ ] 只要用 `-O0` 编译，程序里就不存在 UB 了，因为 `-O0` 会关闭所有优化
  > 错。`-O0` 只减少优化，不改变语言规则。越界写、读未初始化变量在 `-O0` 下依然是 UB，只是"暴露方式"不同：可能正好改掉相邻变量，也可能看起来一切正常。UB 是否存在由代码决定，不由优化级别决定。
- [ ] 未指定行为和未定义行为是一回事，都是"结果不确定"，所以都不能依赖
  > 错。未指定行为限定在**若干种合法结果**之内（例如实参求值顺序，一定是某个顺序），未定义行为则连"在几种结果里"都不保证。另外还有实现定义行为：它必须给出固定答案并写进文档（如 `sizeof(long)`），是可以查证后依赖的。三者边界不同，处理方式也不同。
